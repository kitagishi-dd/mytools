# google-review

Google の Code Review Developer Guide(出典: 本リポジトリ `review/`)に忠実にコードレビューを行う。

## 原則
- 承認可否は「この変更が全体としてコード健全性を改善するか」で決める。完璧さは求めない。改善するなら細部が未完成でも承認してよい。逆に健全性を下げる変更は承認しない(`review/reviewer/standard.md`)。
- 個人の好みでブロックしない。技術的事実とスタイルガイドが優先。複数の妥当な選択肢が等価なら著者の選択を尊重する。
- 人間レビュー固有の論点(応答速度・タイムゾーン・割り込み回避など)はこのRVの対象外。判定は即時に行う。

## 手順1: 引数を解釈する
引数は「レビュー対象の指定」と「自由記述の着眼点」を兼ねうる。既知トークンを対象として先に拾い、残りを着眼点として扱う。引数を受けたら必ず挙動に反映する(黙って無視しない)。
対象トークンは日本語の助詞などと空白なしで連結されることがある(例 `.claude/skills/google-reviewに対して`)。文中から `/` を含む or 既知拡張子のパス片・`#数字`(または引数全体が数字のみ)の PR番号・`A..B`/`A...B` の範囲を抽出し、抽出後の残りを着眼点とみなす。着眼点の文中に現れる裸の数字は PR番号扱いしない。

対象(見つかれば採用。なければ作業ツリー):
- 無指定(既定): 未コミットの変更すべて。tracked は `git diff HEAD`(staged + unstaged)、未追跡の新規ファイルは `git ls-files --others --exclude-standard` で列挙し内容全体を対象に含める(`.gitignore` は尊重)。コミットが無い(HEAD 無し)場合は `git diff HEAD` を使わず、staged は `git diff --cached`、残りは未追跡列挙で代替する。
- PR番号(例 `123`): `gh pr diff 123`。説明は `gh pr view 123`。
- コミット範囲(例 `main...HEAD`): `git diff <range>`。`A..B` は両端点間の差分、`A...B` は分岐点(マージベース)からの差分。ブランチで入れた変更を見るには通常 `A...HEAD`(three-dot)を使う。
- ファイル/ディレクトリパス: 該当パスの差分(なければ内容全体)を対象にする。ディレクトリなら配下を再帰的に対象化する。

着眼点(対象トークンに当たらない自然文。例「セキュリティ重点で」「認証まわりのリスクを見て」「並行性を重点的に」):
- レビューの焦点・追加の関心事として扱う。
- 重み付けに留める。Google ガイドラインの土台(全観点・全行確認・コード健全性での判定)は省略しない。指定観点を最優先しつつ、他観点の重大な問題も見落とさない。

対象と着眼点が混在する場合(例「`master...HEAD` を認証観点で」)は両方を取り出して適用する。差分が空なら、その旨を伝えて終了する。

## 手順2: レビューを進める(navigate.md の3ステップ)
`review/reviewer/navigate.md` の順序で見る。

- Step 1 俯瞰: まず変更の意図(コミットメッセージ / PR本文 / CL説明)を読み、「この変更はそもそも妥当か」を判断する。方向性が根本的に誤っている・不要なら、細部のRVに入る前に理由を添えて即指摘する(後の作業を無駄にしないため)。
- Step 2 主要部: ロジック変更が最も多いファイルを特定して最初に読み、全体の文脈を掴む。重大な設計問題があればこの時点で指摘する(以降のRVが無駄になり得るため)。
- Step 3 残り: 重大な設計問題がないことを確認してから、残りを論理的な順序で見る。テストを先に読むと変更の意図を掴みやすい。

割り当てられた変更行は原則すべて読む。理解できない箇所があれば著者に説明を求める(自分が理解できないなら他の読者も理解できない)。データファイル・生成コード・大規模データ構造は例外。

## 手順3: 何を見るか(looking-for.md のチェックリスト)
各観点を `review/reviewer/looking-for.md` に沿って確認する。

- 設計: 変更はシステムに正しく統合されるか。今このコードベースに属するか。ライブラリ等に置くべきでないか。追加の時機は適切か。最重要の観点。
- 機能: 著者の意図どおり動くか。エンドユーザーと将来の開発者にとって良い挙動か。エッジケース・並行処理(デッドロック/レース)を考慮しているか。UI変更は実挙動を確認したか。
- 複雑性: 必要以上に複雑でないか。「読み手がすぐ理解できない」なら複雑すぎる。過剰設計に注意 — 今解くべき問題だけを解いているか。将来の推測でAPIや抽象を足していないか。
- テスト: ロジックの追加・変更に対応するテストが同じ変更に含まれるか。テストは正しく、変更が壊れたら失敗するか。アサーションは単純で意味があるか。テストコード自体も複雑にしない。
- 命名: 変数・関数・クラス等が、長すぎず内容を十分に伝える名前か。
- コメント: なぜそのコードが在るかを説明しているか(何をしているかではない)。すべて必要か。コードを明確にすれば消せるコメントはないか。
- スタイル: スタイルガイドに従っているか。ガイド外の好みは `Nit:` を付け、ブロックしない。スタイルだけの大規模変更を機能変更に混ぜていないか。
- 一貫性: 既存コード・周辺の規約と整合するか。スタイルガイドが要件なら従う。既存コードの不整合が原因なら別途バグ登録を促す。
- ドキュメント: ビルド・テスト・連携・リリース方法が変わったら、対応するドキュメント(README 等)も更新されているか。削除されたコードのドキュメントは消えているか。
- 文脈: 差分の数行だけでなくファイル全体・システム全体の文脈で見る。小さな複雑性の累積で全体が劣化していないか。
- 「後で直す」を許さない: 持ち込んだ複雑性は同じ変更内で解消させる(緊急時を除く)。別件の既存問題はバグ登録 + `TODO` 参照に留める。

## 手順4: 指摘の書き方(comments.md)
- 人ではなくコードに対して、理由(なぜそうすべきか / コード健全性への影響)を添えて述べる。
- 重要度を明示する: `Nit:`(軽微、対応推奨だが任意) / `Optional:`(検討に値するが必須でない) / `FYI:`(このRVでの対応は求めない参考情報)。ラベルなしは対応必須。
- 理解できないコードは、レビューツール上の説明で済ませず、コード自体の明確化かコードコメント追加を促す(将来の読者に残るのはコード側だから)。
- 指摘は `path:line` 形式で位置を示す。

## 手順5: 判定する(standard.md / emergencies.md)
最後に明示的な結論を出す。根拠は常に「全体としてコード健全性を改善するか」。

- 承認(LGTM): 健全性を改善し、必須の指摘がない。
- 条件付き承認(LGTM with comments): 残る指摘が軽微で、著者が適切に対応すると見込めるとき。
- 要修正: 必須の指摘が残る、または健全性を下げるとき。

緊急変更(`review/emergencies.md`)の定義は、小さい変更で、かつ ローンチ阻止の回避 / 本番でユーザーに重大な影響があるバグ修正 / 重大なセキュリティ穴 / 切迫した法的問題 のいずれか。基準を緩めるのは利用者が明示的に緊急と宣言したときのみ(締切や本番影響などの判断材料はこのRVからは確認できないため、自動では緩めない)。緩める場合はその旨を明記し、後で通常のRVを行う前提とする。soft deadline は緊急ではない。

## 出力
日本語で次の順に端末へ出力し、同じ内容を md に保存する。

端末:
1. サマリ: 対象(差分の出所)・規模(ファイル数 / 変更行数)・判定。
2. 観点別または ファイル別の findings。各項目は `path:line` + 重要度ラベル + 指摘 + 提案。
3. 判定と次アクション。

保存:
- 保存先ディレクトリ `.reviews/`(無ければ作成)。隠しディレクトリにするのは、公開中の guideline `review/` と混同させないため(Jekyll もドット始まりを無視する)。
- ファイル名 `.reviews/<対象識別子>-<日時>.md`。対象識別子は対象を表す文字列(ブランチ名 / PR番号 / `worktree`、パス対象時はパス由来スラッグ 例 `skills-google-review`)。日時は `date +%Y%m%d-%H%M` の出力を使う。
