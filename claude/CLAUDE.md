# General Instructions

## 言語・返答スタイル
- 日本語で返答する
- 簡潔に。結論を先に、根拠は後ろに
- コードや設定値はコードブロックで示す
- ファイル参照は `path:line` 形式

## 作業フロー
- 大きな変更(設定ファイル、複数ファイル横断、セキュリティ関連)は書き込み前に設計案・選択肢を提示してレビューを挟む
- 危険な操作(force push、git reset --hard、データ破壊系)は事前承認
- commit前に動作確認を実施し、結果をユーザに提示する
  - 動作確認とは: 構文チェックだけでなく、実際にスクリプト・コマンド・機能を実行し、期待通りの挙動が実機で確認できたこと
  - 構文チェックのみで完了とみなさない
- commit・pushはユーザの明示的な許可を都度取る（planや会話の流れでの一括合意は不可）
- Hook / スクリプトを書く時は事前に単体テストして結果を提示してから本番反映
- TodoWrite は3手以上の作業のみ。短いタスクには使わない

## コーディング規約
- コメントは「なぜ」だけ書く。「何を」は識別子で表現する
- 不要な抽象化・防御コード・後方互換シムを追加しない
- 既存ファイル編集を優先(新規ファイル作成は必要な時のみ)
- 依頼されない限り README/ドキュメントファイルを作らない

## コードレビュー方針

- 判断基準: 完璧さではなく「全体のコード健全性を改善するか」で可否を決める。改善するなら細部が未完成でも進め、健全性を下げる変更は通さない。
- 設計優先: 最重要は設計。変更がシステムに正しく統合され、今このコードベースに属するか。
- 観点: 設計 / 機能(エッジケース・並行性)/ 複雑性 / テスト / 命名 / コメント / スタイル / 一貫性 / ドキュメント。当該箇所だけでなくファイル・システム全体の文脈で全行読む。
- 過剰設計を避ける: 今解くべき問題だけを解く。将来の推測で API や抽象を足さない(規約「不要な抽象化を足さない」と同義)。
- 複雑性は持ち込んだ変更内で解消: 新たな複雑性を後回しにしない。別件の既存問題は混ぜず、バグ登録 + `TODO` 参照に留める。
- テストを伴わせる: ロジックの追加・変更にはテストを付け、テストコード自体も簡潔に保つ。
- 小さく自己完結した変更: 1変更 = 1つの事柄。リファクタリングと機能変更は分ける(バグ混入が減り、設計を保ちやすく、ロールバックも容易)。
- 変更説明: 1行目は命令形で「何を」を簡潔に、本文に「なぜ・トレードオフ・限界」。
- 指摘の作法: コードに対して理由を添えて述べ、必須でない指摘は Nit: / Optional: / FYI: で区別する。

## 禁止事項

- 質問された際は、質問への回答だけを行う（質問の意図を深読みして、勝手に修正など変更を伴う作業を実施しない）
- Web検索を実施する場合は、現在の日付などを併用して常に最新の情報を入手する
